# J246: scope control for roadmap-item orders (self-widening owns, budget by size)

Demo Project item B-45 (order J191) was refused three times at commit as "scope bloat" (15 files, 1341 lines against 12/800), each time
after a full build. Now a roadmap order learns its scope right after the plan, and its budget follows its size:
- **scope-check station** (`kitchen/stations/scope-check.ps1`, recipe `roadmap-item`, right after the plan): reads the plan's
  `## Files to change` list. A file outside the item's owns that no other unmerged item owns, no running order names (the clash rule's
  file finder, `kitchen/clash.ps1`) and is not protected is **widened**: added to the item's owns in the worktree's roadmap (so the
  merge carries it), to ITEM.md (so the cook may change it) and to the scope record. A file another item owns **stops** the order in
  a minute, naming both ids. So does a plan with more files than the budget, no PLAN.md, or no `Files to change` list.
- **commit** accepts exactly the widened files from the kitchen's own copy of the record (`<kitchen>\scope\<job>.json`; the cook can
  edit `.kitchen\SCOPE.json` but that copy is not trusted), and the roadmap file only byte for byte as scope-check wrote it.
- **Budget by size**: `kitchen.repo.json` `commitBudget.bySize` `{S,M,L}` (files, lines). Size = the order's size var, else the
  roadmap item's, else M. The flat numbers stay the M default.
- **pr** says widened files in plain words. Every widen and stop is a `scope.widen` / `scope.stop` line in `events.jsonl`.

Files: `kitchen/stations/scope-check.ps1` (new), `kitchen/scope-lib.ps1` (new), `kitchen/stations/commit.ps1`, `kitchen/stations/pr.ps1`,
`kitchen/repo-config.ps1`, `kitchen/recipes/roadmap-item.json`, `tests/Test-ScopeCheck.ps1` (new), `tests/Test-Roadmap.ps1`.

## Effect
- L1 (Jordan): an item that cannot land stops in a minute with a reason he can act on, not after an hour of build.
- L2 (business): Demo Project items finish before the 10-27 merge freeze instead of looping on scope bloat.
- L3 (MSP): the same rule works for any repo with a roadmap; limits come from its config, not from a hand-kept list.
- L4 (community): none directly.
