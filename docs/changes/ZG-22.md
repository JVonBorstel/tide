## In plain words

The scoreboard now keeps a trust score for each crew: when the Inspector says "ship" or a build crew says "the tests pass", was it right?
0 means always right, 1 means always wrong. Beside it, the four build-standard numbers (broken mains, false undos, silent failures,
minutes from Floor start to merge), or "unknown" with the missing record named. Nothing about who gets work changes yet.

## What it does

**Crew Brier** (`kitchen/scoreboard.ps1`). Brier = mean (claim - outcome)^2 over the window's improve work orders (the scoreboard's own
population, `-Days`, default 7).

1. **The Inspector's claim.** The review Step's last dish ending `VERDICT: SHIP` is a 1.0 claim that the change is good. Outcome:
   - **0, red on verify**: a `merge.broken` event (verify found main broken by it and could not undo it);
   - **0, undone**: an undo within 7 days of the merge. Undo time = the first `undone` record in `automerged.jsonl` (undo-merge.ps1 and
     verify write them) or the first `merge.undone` event. Merge time = the work order's merge record in `automerged.jsonl`, else its
     `job.done` event. No merge time known = any undo counts;
   - **1, kept**: merged (status done) and no undo within those 7 days. An undo later than 7 days does not count against the Inspector;
   - **no outcome** (not scored): not merged and not undone (still waiting, set aside, closed). A REWORK verdict is not scored.
   - A kept merge younger than 7 days is scored 1 and counted in `brier.pending`, so the reader sees how many can still turn to 0.
   - `verify.main-red` (main was already red, nothing undone) is not held against the work order, the same rule as 0 false undos.
2. **The build crew's claim.** A line in the build Step's first log that says the tests pass (`tests`/`suites`, then at most 3 words,
   then `pass`, `passes`, `passed`, `passing` or `green`; "all tests should pass" counts) is a 1.0 claim. Not a claim: the tests Step's own
   `tests:` lines; a line with `not`, `never`, `cannot`, `could not`, `unable`, `did not`, `fail...`, `unverified`, `untested` or
   `unknown`; and a condition or requirement (`if`, `only`, `must`, `unless`, `either`, `whether`). The last group came from a read-only
   look at the live build logs on 10-24: lines like "it passes only because ..." and "if that ends PARTIAL PASS" were matching. Outcome =
   the tests Step's first run: ends `tests: ALL PASS` = 1, else 0 (the same reading as `firstTryPct`). No tests log = not scored.
3. **Who made the claim.** The model is the last `cost` event's supplier/model for that Step; the kind is the last `cook` event's kind
   for that Step (the `cook` events now keep `job` and `step` in memory; nothing stored changes). Neither = `unknown`.
4. **Output.** JSON `brier = { value, claims, pending, inspector {value, claims}, builder {value, claims}, models {key: {value, claims}},
   kinds [{kind, model, value, claims}], missing }`, and next to `firstTryPct` in every `models` row and every `kinds` row: `brier` and
   `brierClaims` (null and 0 when it made no scored claim). Values are rounded to 2 decimals. `-Record` writes it all to `scoreboard.jsonl`.
   Plain report: `crew Brier 0.44 over 9 claims (...)`, one line per model, one per kind; with no claim, `crew Brier unknown (<sources>)`.

**The build standard's four numbers** (`standard`, the same window; `projects/tide/plans/build-standard-2026-10-23.md`). Each is null with
`standard.missing.<name>` naming the missing source when there is no data. Never a guess.

| Number | Source | Unknown when |
|---|---|---|
| `brokenMains` | `main.status` events with state `red` in the window (verify and recheck-main write one per change of state) | no `events.jsonl`, or no `main.status` event ever and no `main-status` folder |
| `falseUndos` | `merge.undone` events in the window: 0 when every one carries `preMergeSha` (the blame check, TD-EH-01, proved the merge broke it) | no `events.jsonl`, or any undo has no `preMergeSha` ("N of M ... have no preMergeSha") |
| `silentFailures` | none yet | always: nothing records when a failure reached the Board |
| `floorMinutes` (+ `floors`) | Floors = roadmap-item work orders started in the window: `created` to the merge Step's `step.done`, else `job.done`, averaged | no merged roadmap-item work order started in the window. Hand-merged Floors (`merges.jsonl`) have no start time |

Plain report: `build standard: broken mains 1 · false undos 0 · silent failures unknown (...) · minutes Floor start to merge 60 over 2 Floors`.

Floors are read only for these minutes; they are not added to `orders` or to any other number.
