# W4: Chef with no git on the loop, change-driven state, patches and keyed rows (Tide arch-10-22, wave W4; Chef 2.8.0)

Chef did a full job's worth of work for every small change. Each change rebuilt the whole board on the PC and sent all of it to the
phone (182 KB, or 1.46 MB at 10x the orders). The phone then rebuilt every row. Merge-gate git calls froze the server for up to 0.9 s.
Now one job's change costs one job's work, one small patch and one row:
- **No git on the loop**: git and the kitchen's scripts start from one worker thread. Merge gates are measured again only when `main` or
  their branch moved (one `git for-each-ref` per repo every 10 s). Approve and Approve all still measure the diff fresh and wait for
  that check before the kitchen is asked to grant anything (StaleSha_ApproveRefused).
- **Change-driven state**: only the job files Windows names are read; a 60 s sweep stats the rest without blocking. Spend and tokens
  are read from the event index (new bytes only). Small files are re-read only when they change.
- **Patches**: one full state per stream, then `patch` messages with a version; a phone that misses one resyncs once.
- **Keyed rows**: a row is rebuilt only when its own markup changes. On the rail, Set aside and Show all plated show 20 rows at a time.
  The offline copy is saved when Chef goes to the background, not every 5 s.
- **Scene**: draws only on screen (IntersectionObserver), only when the picture changes (frame key), at 30 fps unless a chef walks.
- `/api/health` shows how late the event loop ran (`loop`) and how much the board read (`work`). It is still numbers only.

## Measured (chef.md method; copies of the live state: 289 jobs and a 10x copy of 2,890; main 4bd6ba5 -> this branch)
| | before | after |
|---|---|---|
| board build after one job edit (median of 9) | 30.4 ms (1x), 173 ms (10x) | 8.1 ms, 9.4 ms |
| board build after an event append | 20.4 ms, 34.5 ms | 9.5 ms, 9.5 ms |
| stream message after the first | 182 KB (1x); 10x: the stream was dropped (1.46 MB over the 1 MB cap) | median 469 B, max 2.9 KB |
| worst event-loop delay, 10 merge gates, stream open | 920 ms in 60 s (1x) | 52 ms in 60 s (1x), 37 ms in 70 s (10x) |
| phone work per change, 375x812 (parse + render + layout) | 40-69 ms (1x), 405-630 ms (10x) | 7-13 ms (1x), 13-16 ms (10x; one 59 ms in 6) |

## Effect
- L1 (person): Jordan's phone stays smooth while the kitchen is busy. Before, every change froze it for about half a second at 10x.
  Taps no longer land on rows that are being rebuilt.
- L2 (business): Chef keeps up at 10x the orders. Before, at 10x a phone without compression lost its live stream on the first message.
- L3 (MSP): Approve all no longer stops every phone's stream while git runs. /api/health shows the loop delay, so a slow Chef shows up
  as a number.
- L4 (community): the patch protocol is small and documented (pass-app/README.md "Live board"). `patch.js` and `rows.js` work with no
  dependencies.

## Not done
- No module split (J227/J228): about ten suites grep `server.mjs` and `app.js` text, so the split is churn with no behaviour gain here.
  The new pure parts went into their own files (`patch.js`, `rows.js`).
- Scene frame CPU after the change: unknown. The browser pane was hidden, so requestAnimationFrame never ran (0 frames in 10 s, before
  and after). Its tests (`test-scene.mjs`) prove the stage draws nothing off screen and draws a still picture once, not 30 times a second.
- No full state every 10 minutes: at 10x it would be a 1.4 MB message. The version check plus the replay test bound the drift instead.
- The phone at 10x still spends about 11 ms of script per change: it filters 2,890 jobs into sections on each change. Splitting the
  state by active jobs (J267's first part) is the next step.
