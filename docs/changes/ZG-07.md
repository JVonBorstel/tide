## What it does

**The lobe Step** (code: `kitchen/stations/lobe.ps1 -Cmd sweep|rem|csf|health`):

1. **Finds the zeitgeistd checkout.** In order: env `ZEITGEISTD_REPO`, then `kitchen.json` `"lobe": {"repo": "<full path>"}` (the
   state-folder copy first, then this repo's), then `<user profile>\source\repos\zeitgeistd` (on this PC,
   `%USERPROFILE%\source\repos\zeitgeistd`). A folder without `pyproject.toml` and `zeitgeistd\__init__.py` is refused.
2. **Sets up the lobe home.** `ZEITGEISTD_HOME` is `<kitchen>\lobe`. `<kitchen>\lobe\config.json` gets
   `"heartbeat_path": "<kitchen>\watch\lobe.json"`, so the Watch reads the lobe's heartbeat with no change to the Watch. Other keys
   stay. A config.json that is not a JSON object is never overwritten: the Step stops with exit 1.
3. **Gates the commands that may call a model.** These are sweep and rem. They need free RAM of at least 2,500 MB
   (`kitchen/scaler.ps1` `Get-ScalerFreeMB`) and a ready Ollama (`kitchen/cooks/local.ps1 -Probe`). When a gate stops the run:
   - the Step prints which gate stopped it;
   - it writes the skip into the heartbeat with `health --skip "<why>" --run <cmd>`;
   - it exits 11. In the Yard that means wait, with no retry used, as `kitchen/stations/ci-wait.ps1` does. The wait is 900 s, the
     Yard's own default.

   An Ollama address that is not this PC is a refusal, not a wait: exit 1, and no lobe module runs. csf and health only read, so they
   have no gates.
4. **Holds the GPU lock.** sweep and rem hold `Global\brain-kitchen-gpu`, the lock `kitchen/cooks/local.ps1` holds. If the lock is
   still busy after 60 s, the run is skipped the same way, with exit 11.
5. **Runs the lobe through uv.** The command is `uv run --locked --quiet python -I -m zeitgeistd.<module>`, in the checkout, with
   `UV_PYTHON_PREFERENCE=only-managed`. The API key variables are removed first: the list from `kitchen/cooks/claude.ps1` and
   `cooks/agy.ps1`, plus any `*_API_KEY` or `*_AUTH_TOKEN`. `KITCHEN_OLLAMA_URL` is passed through.
   - **sweep** runs `db init`, `connectors.yard`, `connectors.git`, `actions run`, `csf`, then `gate sweep`. The gate goes last because
     its heartbeat carries the sweep's stop reasons and a failed sweep's error, and a later csf run would overwrite them. A failed
     `db init` stops the sweep; any other failed step does not stop the rest.
   - **rem** runs `zeitgeistd.rem` (ZG-28). The checkout has no `rem.py` yet, so rem is refused today and says so.
   - **csf** runs `csf`, and **health** runs `health`.
6. **Ends with one line.** It prints `lobe: <cmd> done items=N dropped=N ms=N` only when every module exited 0. items and dropped
   come from the module's own ok line: the gate's `processed=` and `dropped=`, or rem's `items=` and `dropped=`. csf and health take in
   nothing, so theirs are 0. Otherwise it prints `lobe: <cmd> FAILED (...)` and exits with the first failing module's code. A module's
   10 or 11 becomes 1, so a failure is never read as a hold or a wait.

**The Specs** (code: `kitchen/recipes/lobe-sweep.json`, `lobe-rem.json`) each have one Step, `lobe` with `Cmd`. They have no agent Step:
no crew, no prompt, no model name, no tools. Their mustMatch is the done line:

| Spec | Time limit | Memory |
|---|---|---|
| lobe-sweep | 300 s | 1,500 MB |
| lobe-rem | 900 s | 2,000 MB |

Both use `retries 0`, so a failed run shows as Failed and the next standing run comes on its clock.

it has no lobe line. When you want the lobe on a clock, add these two lines to `"standing"` in `kitchen.json`. The 4 am hour is
inside the 4-5 am window that the file's `_standing` note names.

```
{ "name": "lobe sweep", "recipe": "lobe-sweep", "everyHours": 2 },
{ "name": "lobe rem", "recipe": "lobe-rem", "everyHours": 24, "atHour": 4 }
```

Before you add them, set these keys in `<kitchen>\lobe\config.json`. Without models, the gate refuses every sweep (exit 3, Failed):
- `"models.fast": "tev1:0.8b"` and `"models.triage": "qwen2.5:3b"` (ZG-11's note);
- the `yard.*` paths (ZG-03's note);
- `git.repos` (ZG-04's note).

Add the lobe-rem line only after ZG-28 merges. Until then, rem is refused by design.

## Measured: what the kitchen-sandbox Low run can start (ZG07-4)

The exe is the built `rust/kitchen-sandbox/target/release/kitchen-sandbox.exe` of the main checkout. The flags are those of
`Get-KitchenSuiteCommand`. Every run used a fresh temp kitchen.

- The integrity level inside is `Mandatory Label\Low Mandatory Level` (`whoami /groups`).
- **The WindowsApps `python.exe` alias at Low is unreliable.**
  - 21 Low runs of `python.exe -I -c ...`: 15 started Store Python 3.13.14
    (`C:\Program Files\WindowsApps\PythonSoftwareFoundation.Python.3.13_3.13.3824.0_x64__qbz5n2kfra8p0`), and 6 printed the Store
    stub's "Python was not found ..." with exit 9009.
  - No flag explained it. Working folder, `--path-first` and probe text were each varied, 2 runs each, and both outcomes appeared.
  - At Medium (a normal shell), 3 of 3 runs started it.
  - The lobe Step never uses the alias. It uses uv and the uv-managed Python.
- **uv at Low.**
  - `uv run --locked --quiet python -I -c ...` in the checkout, without `UV_PYTHON_PREFERENCE`, worked (exit 0, the checkout's
    `.venv` python).
  - With `UV_PYTHON_PREFERENCE=only-managed`, as the Step sets it, `uv run --locked` tried to rebuild the checkout's `.venv` and was
    denied: `failed to remove file ...\.venv\.gitignore: Access is denied`. The sandbox gives a suite a private APPDATA, so uv cannot
    see the managed Python the `.venv` was made with. The `.venv` was unchanged afterwards (same timestamps, `git status` clean).
  - `uv run --locked --no-sync` with only-managed worked at Low.
- **What that means for the test.** The test's real call to the checkout's health runs only where uv sees the `.venv`'s Python
  (`pyvenv.cfg` `home` under `UV_PYTHON_INSTALL_DIR`, else `%APPDATA%\uv\python`). Anywhere else it prints a `SKIP:` line with the
  reason, never tries, and so can never damage the checkout. This also covers a Medium sandbox run, which has the same private APPDATA.
- **The Step itself runs at Medium.** kitchen-step runs Steps in its own process, and only the tests, mutate and verify Steps use the
  sandbox. So the Yard's lobe runs are not affected by this.

## Decisions (each is a choice, not a guess)

- **sweep is connectors + gate + frame.** INTEGRATION-MAP section 4 ("connectors + `lobe-sweep` recipe") makes the lobe-sweep Spec
  the one that runs the connectors. ZG-12 says no Step ran `actions run` yet and names ZG-07. `db init` is idempotent, and a fresh lobe
  home needs it.
- **The gate goes after csf**, so the heartbeat the Watch reads is the gate's own. The frame then reflects the previous sweep's scores
  (one sweep behind). The alternative, csf last, would replace a failed sweep's heartbeat error with csf's, and the Watch would miss the
  failure.
- **Gates only for sweep and rem.** Blocking `health` while Ollama is down would hide the lobe's state exactly when it matters. An
  unknown RAM reading (no `Win32_OperatingSystem`) is printed as unknown and does not stop the run, as ZG32-3 rules for missing signals.
- **The default checkout path is built from the user profile**, which is `%USERPROFILE%\source\repos\zeitgeistd` on this PC. A second
  Yard (the Razer) finds its own checkout the same way.
- **config.json is written by the Step only to set `heartbeat_path`.** The lobe never writes config.json (ZG-01). The models, yard
  paths and repo list are your choices, so they are listed above for you, not written.
