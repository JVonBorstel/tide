# TD-10: sandboxMedium and Staffing weights keyed by Tower

Floor TD-10 of Site TD (TD Pour 2), from `projects/tide/plans/multi-site-design-2026-10-23.md` section 2.5 and the Floor table.
Branch `ms-td10-tower-weights`, stacked on TD-12 (`ms-td12-inspector`, PR #129) at `c6847ba`, built 2026-10-24.
Merges after #129 (both touch `kitchen/stations/tests.ps1`).

## What it closes

Two leaks between Sites named in the design: a `sandboxMedium` suite name held in every Tower (`Test-Phase0` is Demo Project's, but a
brain-monitor suite of that name got the same Medium rule), and one Staffing weight per station, so a Demo Project `tests` run and a TD
`tests` run shared one weight.

## What it does

- **`sandboxMedium` keyed by Tower** (`rust/kitchen-sandbox/sandbox.ps1`): an entry whose value is a list stays global, exactly as
  before. An entry whose value is an object is a Tower block, named by the Tower's main checkout folder (any case):
  `"demo-project": { "Test-Phase0": [...] }`. A suite in its Tower's block uses that list and wins over a global entry of the
  same name; a Tower block never reaches another Tower. A block entry that is not a list of file names is dropped (that suite runs
  Low). The old guards hold: a job that touched a listed file, or the suite file itself, runs Low.
- **Which Tower:** the tests station passes the repo name it already works out for suite times (`Get-SuiteRepoName`). A caller that
  passes none (the mutate station) gets it from the folder's git common dir, and only when a Tower block exists, so a config without
  blocks costs no git call.
- **Weights keyed by station + Tower** (`kitchen/scaler.ps1`, wired in `kitchen/kitchen.ps1`): a finished run of an order with a Tower
  (`vars.repo`, else a step's `Repo`) is kept under the station, as before, and under `station@tower` (`tests@demo-project`).
  Admission judges a step by its Tower's entry once that entry has 3+ runs, else by the station's entry. Running steps' unclaimed
  weight uses their own Tower's entry too. The doctor's slots line lists the `@` entries next to the station ones.
- **Kept:** TD-EH-19's median climb (`Update-KitchenScaler`, `Test-ScalerHighWindow`) is untouched, and so is #95's memory cap (the
  sandbox `--mem` of twice `MaxMB`, the station's `stopMB`). Their checks pass unchanged.
- **Not touched:** the live `kitchen.json` (state folder), `kitchen/github-lib.ps1` and the chores CI counts (TD-11's).

## Without per-Tower keys: exactly as today

- No object entries in `sandboxMedium`: the suite command is byte for byte the same with a Tower and without (24 cases).
- No `@` entries in `weights.json`: every admission answer (ok, light, why) is the same with a Tower and without (48 cases), and a
  run with no Tower writes only the station entry. The repo `kitchen/kitchen.json` keeps its list entries as they were; only its
  notes changed.

## The block Jordan would add (Owner step, not done here)

The live state-folder `kitchen.json` (`%LOCALAPPDATA%\brain-kitchen\kitchen.json`) has no `sandboxMedium` today, so the repo copy's
global list applies. To key the three suites by their Tower, add this to the state copy. It replaces the repo copy's list as a whole,
so it names all three:

```json
"sandboxMedium": {
  "brain-monitor": {
    "Test-Rgb": ["tests/Test-Rgb.ps1", "scripts/rgb.ps1", "scripts/stable-pwsh.ps1"],
    "Test-ApplyFill": ["tests/Test-ApplyFill.ps1", "kitchen/apply-fill.mjs", "tests/fixtures/apply-fill/server.mjs"]
  },
  "demo-project": {
    "Test-Phase0": [".claude/", "scripts/", "tests/phase0/"]
  }
}
```

Weights need nothing set: the `@` entries fill in as orders finish, and each takes over after its third run.
